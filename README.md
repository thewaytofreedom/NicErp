# NicErp

Next.js 管理端 + NestJS 模块化后端 + PostgreSQL / Prisma 的独立 ERP。
当前版本 0.2.0。仅使用 NicErp 自己的代码与数据库，不依赖或修改 epl、Dolibarr。

## 启动

需要 Node.js 22.12+（22 LTS）、npm 10+、Docker Compose v2。

首次部署：

```sh
npm ci
cp .env.example .env
cp apps/api/.env.example apps/api/.env
cp apps/web/.env.example apps/web/.env.local
```

本机已有环境文件，不要覆盖。新环境请将 `.env` 的 `POSTGRES_PASSWORD` 和 API 环境文件连接 URL 的密码设为同一个随机密码，URL 特殊字符须编码。

```sh
npm run db:up
npm run db:generate
npm run db:push
npm run dev
```

- 管理端：http://localhost:3000
- NestJS API：http://localhost:3001/api/v1
- Swagger（开发模式）：http://localhost:3001/api/docs
- PostgreSQL：127.0.0.1:5433，独立 `nicerp` 数据库和 Docker 数据卷

第一次访问会进入初始化页面：填写公司名称、本位币、管理员姓名、邮箱和至少 12 位密码。没有内置演示密码或预设管理员。初始化完成后只显示登录页。

当前开发公司已按需填充带 `DEMO-` 编号或“测试”名称的演示业务数据；自动测试写入独立 `nicerp_test` 数据库。

基础演示数据可使用 `node --env-file=apps/api/.env scripts/seed-demo.mjs` 添加，包括产品、往来单位、仓库、账户、期初库存与单据草稿。脚本通过业务服务写入，不清空数据；重复执行跳过已有资料，期初库存使用幂等请求键。存在多个公司时，须通过 `DEMO_COMPANY_ID` 指定目标公司。

## 日常操作顺序

1. 初始化公司与管理员；在系统设置中配置本位币和公司资料。
2. 建立品牌/分类/系列、产品、客户及供应商、仓库和资金账户。
3. 库存期初使用“库存 → 调整库存”；日常进货优先使用采购订单收货。
4. 创建报价草稿 → 确认 → 转销售订单 → 确认 → 分批发货。
5. 销售订单可转采购草稿（选择供应商，按本位币参考成本生成）；核对供应商报价再确认、收货。
6. 销售/采购订单转对应发票草稿，确认后登记收付款。
7. 收发货录错时使用退回；付款录错时在收付款流水中冲销。原始流水保留。

## 权限

所有用户都必须属于所选公司。读权限允许查看该公司的业务资料；只有管理员能读取用户列表与完整审计日志。当前角色定义主要限制写入，不做成本字段级隐藏。

| 角色 | 写入权限 |
| --- | --- |
| ADMIN 管理员 | 当前公司全部功能、成员管理、新增公司 |
| MANAGER 业务经理 | 产品、往来单位、销售、采购、库存、财务、内容 |
| SALES 销售 | 产品资料、往来单位、销售 |
| PURCHASING 采购 | 产品资料、往来单位、采购 |
| WAREHOUSE 仓管 | 仓库、库存调整/调拨、已确认订单收发货与退回 |
| FINANCE 财务 | 发票、资金账户、收付款及冲销 |
| VIEWER 只读 | 仅业务读取 |

跨模块转换要求同时具有来源与目标模块写权限。为已有邮箱添加成员只增加其公司权限，不更改其密码或账号状态。每个公司必须保留至少一名启用的管理员，停用、降级和移除权限均在串行事务中检查。

系统设置的“用户权限”可查看和编辑账号启用状态。账号状态对所有公司生效；启停跨公司账号时，操作者须在该账号所属的每家公司拥有管理员权限。停用撤销该账号全部会话并拒绝登录，重新启用后须重新登录。角色变更和公司权限移除会在下一次请求立即生效。密码修改撤销该用户全部会话；前端收到 401 时清理会话与公司 Cookie。

## 核心业务规则

- 单据编号在公司内唯一，单据作废后不回收编号。
- 报价明细默认从 1 自动编号，可在序号列输入不同的正整数（最大 1,000,000），回车或离开输入框后按数值排序。新增行接续最大序号，手动序号允许留空档；重复序号不能保存。序号随草稿保存、报价复制、单据转换及打印保留，CSV 模板也包含可选序号列。标题、备注和小计同样编号，小计按排序后的分组重算。
- 只有草稿可编辑；版本号检查防止覆盖其他人的修改。确认后保留客户、价格、税率、成本与组合零件结构快照。
- 数量/单价最多 4 位小数，汇率最多 6 位小数，金额按行四舍五入到 2 位；先行折扣，再整单折扣，再计算税额。服务端使用 Decimal 计算。
- 汇率定义：1 单据币种 = 汇率 × 公司本位币。本位币单据汇率必须是 1。有产品/单据后不能改变公司本位币。
- 单据转换保留关联关系，每种目标类型只允许一个未作废下游单据。转换目标为草稿，可在确认前核对。
- 库存使用 Serializable 事务、冲突重试和流水，禁止负库存、超量履约。库存调整、调拨、收发货、收付款带幂等请求键。
- 退回数量不得超过所选仓库的已履约净数量。退回后订单重新开放未履约量，不自动生成退款或贷项单。
- 组合产品为虚拟套件，库存保存在组成零件上；支持嵌套组合，禁止循环；同一叶子零件的用量合并。服务履约不产生实物库存流水。
- 仓库有库存时不能停用。已经使用的产品不允许改变类型；主数据使用停用状态保留历史关联。
- 收付款不能超过发票未付金额，账户和发票必须同币种。资金余额允许为负以表达透支；付款冲销保留记录并恢复未付余额。
- 作废有约束：必须先退回已履约数量、冲销全部付款，并作废有效下游单据。
- CSV 主数据导入每次最多 200 行，逐行提交并报告成功数量/错误行号；可用模板。单据明细 CSV 导入替换当前编辑器明细，保存时由服务端统一校验。
- 单据产品明细输入产品编号或替代号，回车或点击“匹配”；唯一精确匹配自动填入，多个匹配须确认，无精确匹配时按产品编号片段查找。匹配查询当前公司的全部有效产品，不受预加载数量限制。明细 CSV 的产品编号也可填写替代号，但必须唯一精确匹配。
- 列表每页 25 条，导出当前搜索结果最多 10,000 条；选择器当前最多加载 1,000 条有效主数据。导出对表格公式前缀做转义。

完整 Dolibarr 对齐工作和逐模块未完成项见 [功能验收清单](docs/dolibarr-parity.md)，本版本尚未全部对齐。

## 当前边界

这一版可以操作上述业务流程，但并非完整会计系统：

- 毛利使用产品参考成本快照，没有 FIFO/移动加权库存计价、总账、凭证、税务申报、跨币种付款/汇兑损益。
- 订单确认不预占库存，不做采购审批层级或自定义工作流。流程使用明确的确认、转换、收发货动作。
- 发票按整张订单转换，不支持部分开票、贷项通知单或退货退款的自动财务冲销。
- 图片采用 URL 维护，文章为安全纯文本；未增加图片上传/附件存储服务、富文本编辑和邮件发送。
- 产品展示标记与文章发布状态不向外部网站推送。epl 代码、接口和数据库保持独立。
- 当前只对单据草稿实现乐观锁；基础资料采用最后一次成功保存。

## 会话与部署

会话令牌使用随机值，数据库只存其哈希，浏览器使用 HttpOnly、SameSite Cookie，8 小时有效期。NestJS 每次验证公司成员权限；Next.js 写接口校验 Origin 与实际 Host。密码使用带随机盐的 scrypt；登录有限流；前端不持有数据库连接或可读会话令牌。

开发管理端监听 0.0.0.0:3000，可通过服务器 IP 从局域网访问；API 与生产管理端默认绑定 127.0.0.1。本机开发使用 `npm run dev`。正式模式：

```sh
npm run build
NODE_ENV=production npm run start -w @nicerp/api
npm run start -w @nicerp/web
```

两条 start 命令各占一个终端。生产管理端启用 Secure Cookie，需要 HTTPS；反向代理须正确保留 Host。配置持久进程管理、备份和 HTTPS 后再对外部署。生产环境会关闭 API Swagger。

`db:push` 目前用于开发库表结构同步；正式上线前改为有版本的 Prisma schema migrations。停止容器使用 `npm run db:down`，保留数据卷。

## 验证

```sh
npm run typecheck

集成测试使用与开发库同一 PostgreSQL 实例中的 **nicerp_test**。首次测试可执行：

docker compose exec -T postgres createdb -U nicerp nicerp_test
npx playwright install chromium
```

`test:business` 将连接 URL 的数据库名称固定替换为 `nicerp_test`，同步测试表并清空测试数据，绝不在 `nicerp` 库清表。浏览器测试使用 3100 端口和随机 API 端口，不使用 3000 的开发实例。测试截图与 PDF 保存于 `artifacts/`（已忽略）。

测试涵盖登录/初始化锁、账号启停及会话撤销、登录与停用并发、角色即时变更、最后一名启用管理员的并发保护、跨公司账号管理权限、登出/过期/密码修改、公司隔离、输入校验、精确折扣税额、单据转换、分批履约和退回、库存幂等与并发、组合产品、仓库调拨、多币种、收付款及冲销、版本冲突、内容和导入错误反馈，以及实际浏览器录入/打印操作。用户回归场景集中在 `scripts/test-user-lifecycle.mjs`，随业务测试执行。

## 目录与 API

```text
apps/api/src/
  auth/        会话、初始化、登录、权限上下文
  common/      输入校验、角色策略、统一错误
  database/    Prisma、串行事务重试、审计记录
  erp/         主数据、单据与库存/资金业务服务
  health/      存活与数据库就绪检查
apps/web/src/
  app/(erp)/   受保护工作台、模块、单据与内容预览
  app/login/   首次初始化与登录
  app/api/     Cookie 会话代理与公司切换
  components/  列表、表单、明细编辑、业务操作对话框
  lib/         表单配置、接口、CSV、安全辅助
scripts/       冒烟、API 集成、浏览器测试
```

业务 API 统一 `/api/v1/erp`；身份 API `/api/v1/auth`。直接调用需要 `Authorization: Bearer <session-token>` 和 `X-Company-Id`（省略时使用用户第一个公司）。管理端通过服务器代理调用，不向客户端暴露令牌。

主要端点：

- `GET /erp/bootstrap`、`GET /erp/dashboard`
- `GET/POST /erp/{products,partners,lookups,warehouses,accounts,posts,users}`，`PATCH /erp/{resource}/:id`
- `GET /erp/{stock,movements,payments,audit}`
- `POST /erp/company`、`POST /erp/companies`、`DELETE /erp/users/:id`
- `GET/POST /erp/documents`，`GET/PATCH /erp/documents/:id`
- `POST /erp/documents/:id/{confirm,void,convert,fulfill,pay}`
- `POST /erp/inventory/{adjust,transfer}`、`POST /erp/payments/:id/reverse`
- `POST /erp/import/{products,partners}`

Swagger 列出路由；复杂请求样例见 `scripts/test-business.mjs`。

依赖固定在 package-lock.json。根 overrides 为 Swagger/Prisma 间接依赖的修复版本；升级时重新评估。使用 `npm run format` 统一代码格式。
